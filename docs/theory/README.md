# `docs/theory/` — справочно-теоретический слой OptiVibe

**Что это.** Поблочная теоретическая документация цифрового двойника ВОД вибрации:
для каждого функционального блока прибора — полный вывод физической модели, проверки
(размерность, предельные случаи, литература), числовые примеры на величинах базы и точное
соответствие реализующему коду. Слой **глубже** пользовательского руководства
(`docs/manual/`, стандарт 15): руководство отвечает «куда нажать и зачем», а этот слой —
«откуда взялась каждая формула и где она в коде».

**Статус слоя.** Учреждён итерацией 1 чата теории (см. аддендум к 15 и запись SW-53 в
журнале 13). Легитимность, аудитория, отношение к руководству и формат зафиксированы в
**аддендуме стандарта 15** (раздел «Справочно-теоретический слой `docs/theory/`»).

---

## Аудитория

- Инженеры по механике / оптике / детектированию / ПО, которым нужен **вывод**, а не только
  результат: как получена `f₁`, откуда `θ/Δ = 1.377/L`, почему `∂η/∂Δy = 0` в первом порядке.
- Новые члены команды (углублённый онбординг поверх руководства).
- Рецензенты физбазы и V&V: слой связывает решения `R-..` / `SW-..` с конкретными функциями.

Не заменяет: физбазу 00–08 (первоисточник чисел и решений), руководство `docs/manual/`
(продуктовый слой), API-справку mkdocs (`docs/reference.md`, автогенерация из docstring).

---

## Источники истины (тот же принцип, что в 15 §2)

Слой — **производный**. Он ничего не решает самостоятельно и не вводит новых чисел:

- **Физика и числа** — из 00–08; решения цитируются по номерам `R-..` (журнал 06), не
  переписываются как новые.
- **Факты о коде** (имена функций, ключи реестров, контракты, стек) — из **реального
  репозитория**, сверенные при написании блока, а не по памяти. Упрощённые фрагменты —
  помечаются явно.
- Если вывод вскрывает пробел/несоответствие в базе — он **не** правится здесь: фиксируется
  как открытый вопрос координатору (в конце блока и в записях 06/13), см. 15 §2.

Честность «реализовано vs замысел» обязательна в каждом блоке: (а) смоделировано в коде — с
модулем/функцией; (б) замысел/дорожная карта — со ссылкой на 07/08/20. Реального железа,
прошивки, АЦП-тракта и потоковой обработки НЕТ (план 20; осциллограф РВ — бэклог S-03).

## Структура каталога

```
docs/theory/
  README.md                 # этот файл: назначение, аудитория, источники, шаблон блока
  usage_modes.md            # сквозной обзор режимов: forward / analyze (S-02) / real-time (замысел)
  01_sensing_element.md     # Чувствительный элемент  (вибрация → консоль → q_tip → η → S)   ← готов
  02_optical_path.md        # Оптический тракт (источник, зазор, циркулятор, опорный/балансный канал)
  03_photodetection.md      # Регистрация оптического сигнала (ФД, трансимпеданс, шумы, АЦП)
  04_hardware_processing.md # Обработка железом (электроника, путь данных от АЦП) — преимущественно замысел
  05_software_firmware.md   # Логика ПО/firmware (DSP-конвейер, S-02, обратная задача)
  tools/
    build_theory.py         # опциональная локальная сборка md → self-contained HTML (MathJax)
```

Порядок `01…05` соответствует физическому ходу сигнала (карта блок → источники/модули — в
промпте чата теории и в 15). `usage_modes.md` — сквозной, читается первым или последним.

**Соответствие блок → источники физбазы → модули кода** (стартовая карта; уточняется по коду
в каждом блоке):

| Блок | Физбаза | Модули кода |
|---|---|---|
| 01 Чувствительный элемент | 02, 03 (+аддендум форм), 05, 08 | `mechanics/`, `optics/`, `core/types`, `excitation/` |
| 02 Оптический тракт | 03, 07 (§источник/опорный), 08, 04 | `optics/` (частично), `core/config` — **больше замысла** |
| 03 Регистрация сигнала | 07 §1, 05 | `detector/photodiode.py`, `dsp/calibration.py` — АЦП частью замысел |
| 04 Обработка железом | 07/08/20 | нет реального HW — **замысел**, требования выводятся |
| 05 Логика ПО/firmware | 09, 10, 11, 17 | `dsp/`, `analysis/instrument.py`, `pipeline/`, `io/`, `cli/` |

## Канонический шаблон блока (обязательный)

Каждый файл-блок оформляется по семи разделам (совместимо с духом «пяти блоков» 15 §4, но с
полными выводами вместо продуктовых описаний):

1. **Назначение.** Что за блок, его границы в цепочке датчика, что именно раскрываем и что —
   нет (передаётся соседним блокам).
2. **Физическая модель и допущения.** Словесная модель + **явный** список допущений с
   **границами применимости** (диапазоны 0.1–50g, линейность, плоскостность, параксиальность).
3. **Математическое описание с выводами.** Формулы с выводом; после каждого ключевого
   результата — **проверка размерности**, **предельные случаи** и **ссылка на литературу**.
4. **Числовые примеры.** На реальных величинах базы (эталон — **вариант B**: `L=2.0 мм`,
   `R_c=31 мкм`, `A=31 мкм`, `Δx₀=0.992 мкм`, `λ=1550 нм`). Числа воспроизводятся из моделей
   кода, а не из памяти.
5. **Реализация в коде.** Методы/функции/контракты (вход-выход), ключи реестров, стек и
   библиотеки, ссылки на файлы репозитория (`main`). Упрощённые фрагменты — помечены.
6. **Замысел vs реализовано.** Явное разделение (а)/(б) по подпунктам блока.
7. **Ссылки.** На документы 00–20 и решения `R-..` / `SW-..`; открытые вопросы координатору.

## Формат и отображение

- **Источник** — русский Markdown с математикой LaTeX: `$…$` для строчных, `$$…$$` для
  выключных; многострочные выкладки — окружения `aligned`/`align`, совместимые с MathJax.
  HTML руками **не** пишется (правило источников 15 §2).
- **Отображение** — опциональный локальный build-таргет `tools/build_theory.py`: сборка
  `md → html` с **вложенным (self-contained)** MathJax (без CDN, открывается офлайн). Используется
  **MathJax, не KaTeX** (полнее по повыводным конструкциям). Публикации на GitHub Pages нет —
  согласно **O-SW-04** (пересмотрен SW-48: хостинг — локальная сборка). Собранный HTML —
  локальный артефакт, **не версионируется** (по аналогии с `.docx` руководства, O-SW-09).
- `.docx` не делаем, если координатор не попросит.

Ворота репозитория (18 §5/§6) слой не нарушает: документация код не меняет; при добавлении
`tools/build_theory.py` — `ruff`/`format`/`mypy` должны быть зелёными.
