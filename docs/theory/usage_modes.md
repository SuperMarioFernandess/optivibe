# Режимы использования (сквозной обзор)

Этот файл — сквозная привязка теоретических блоков к тому, **как** двойник используется.
Он не дублирует блоки: показывает, какая часть цепочки задействована в каждом режиме и где
проходит граница «реализовано / замысел». Опора: 09 (архитектура), 11 (симулятор),
`analysis/instrument.py`, `cli/main.py`.

## (а) Синтетическое моделирование — прямая задача (forward)

Полная цепочка блоков 1→5 в прямом направлении: сценарий возбуждения → механика → оптика →
детектор → DSP. Запуск: `optivibe run <scenario.yaml>` (также `report`, `sweep`).
Задействует всё, что выведено в блоке 1: `Excitation → TipState → OpticalResponse →
DetectorOutput`. Это основной режим верификации (планы 18/19). **Реализовано.**

## (б) Обработка реальных данных — роль S-02 (analyze)

Анализ **выхода** прибора (запись фототока/оцифрованного сигнала) в обход прямой модели:
`optivibe analyze <spec.yaml>` → `analysis.instrument.analyze_record(...)`. Из блоков
задействуются только **обратные** части: калибровка `s_target` и восстановление ускорения
(блок 5), с источником чувствительности `model` (cylinder-only, граница G9) / `measured`
(эталон Э-3) / `bench` (парный эталон). Прямые блоки 1–4 при этом **не** исполняются — на
вход подаётся уже измеренный сигнал. **Реализовано (SW-52).**

## (в) Реальное время — потоковый «осциллограф» (замысел)

Непрерывная потоковая обработка сигнала прибора в реальном времени. **Не реализовано** —
бэклог S-03 (P2), 14 §8. Точка расширения — над `analyze_record`: тот же обратный тракт
блока 5, но на скользящих окнах вместо цельной записи. Требования (буферизация, латентность,
частота обновления) выводятся из полосы 00 и АЦП-требований блока 3. Не выдавать за
реализацию.

---

**Граница «реализовано/замысел» по режимам:** (а) и (б) — реализованы и верифицированы;
(в) — замысел. Реального железа, прошивки и потокового АЦП-тракта нет (план 20; блоки 3–4
раскрывают требования как замысел).
